# SoloPact 实施路线图

**产品定位：** 一人公司的经营承诺与现金流 Agent  
**品牌主张：** Business commitments, under control.  
**当前日期：** 2026-11-05  
**比赛截止：** 2026-11-24

## 1. 实施原则

- 所有金额、到期日和业务状态由确定性规则计算；模型负责理解文本、提出候选和生成语言。
- 合同、邮件和附件都是不可信输入；模型不得因正文中的指令自行调用发送或修改工具。
- 低置信度提取、组合核销、合同变更和所有外发内容必须人工确认。
- 每个业务事实必须保留来源文件、版本、页码或邮件原文，能够从结论回到证据。
- 比赛前只增加能进入主演示链路的功能；其他想法保留在赛后路线图。
- 不提供会计、税务、法律或投资结论，不自动删除邮件，不自动发送外部消息。

## 3. 比赛前关键路径

以下任务按依赖顺序实施。每完成一项就运行后端测试、前端 lint、类型检查和生产构建。

### 阶段 A：业务事实基础

- [ ] `CORE-01` 通用经营承诺模型
  - 交付：新增 `BusinessCommitment`，支持付款、验收、开票、交付和客户承诺五种类型。
  - 字段：责任方、金额、触发条件、计划日期、状态、置信度、证据来源、人工确认状态。
  - 验收：未确认的承诺不能改变应收状态；所有修改进入审计日志。
  - 依赖：无；后续条件付款和邮件提取都依赖此项。

- [ ] `CORE-02` 条件型付款节点
  - 交付：支持固定日期、签约后 N 日、验收后 N 日、开票后 N 日和人工补充触发日期。
  - 验收：缺少触发事件时显示“等待验收/等待开票”，不得虚构到期日；补充触发日期后确定性计算到期日。
  - 测试：自然日/工作日、缺失触发日期、重新计算和租户隔离。
  - 依赖：`CORE-01`。

- [ ] `CORE-03` 发票与验收最小闭环
  - 交付：发票支持待开、已开、已送达、退回；验收支持待验收、已验收和存在异议。
  - 验收：发票或验收状态能激活对应付款节点；附件可以回到文档中心和原始证据。
  - 依赖：`CORE-01`、`CORE-02`。

- [ ] `CORE-04` 部分付款与组合核销
  - 交付：记录已收和剩余金额；支持多笔流水对应一个节点、一笔流水覆盖多个节点的候选建议。
  - 验收：一对一精确匹配可自动确认；部分或组合匹配只能人工确认；同一流水不能被重复占用。
  - 测试：部分付款、组合付款、拆分付款、重复运行和金额差异。
  - 依赖：`CORE-02`。

- [ ] `CORE-05` 客户付款承诺追踪
  - 交付：从粘贴文本或邮件中提取承诺金额、日期、条件和原文，人工确认后进入跟进计划。
  - 验收：到期后自动与流水比对，得到已兑现、部分兑现、未兑现或待确认状态。
  - 依赖：`CORE-01`、`CORE-04`。

### 阶段 B：经营收件箱

- [ ] `MAIL-01` 邮件领域模型与演示邮箱
  - 交付：新增账号、线程、邮件、分类、建议动作、回复草稿和发送记录；Docker Compose 加入 Mailpit。
  - 验收：能够载入合成邮件、展示完整线程，并在本地邮件沙箱中接收真实发送结果。
  - 依赖：`CORE-01`。

- [ ] `MAIL-02` 邮件分类与行动路由
  - 交付：分类为无需处理、需要回复、需要决策、转交审阅、业务材料、风险邮件和疑似垃圾/钓鱼。
  - 验收：展示分类理由、置信度和建议动作；低置信度邮件进入人工分类，不自动删除或归档。
  - 测试：模型结构校验、规则降级、提示注入文本和人工纠正。
  - 依赖：`MAIL-01`。

- [ ] `MAIL-03` 邮件关联业务与附件入库
  - 交付：按发件人、客户别名、合同编号和线程上下文关联客户与合同；附件进入现有文档处理链路。
  - 验收：验收邮件可以激活付款节点，补充协议进入待确认版本，付款回复生成待确认承诺。
  - 依赖：`MAIL-02`、`CORE-02`、`CORE-03`、`CORE-05`。

- [ ] `MAIL-04` 审核并发送
  - 交付：在原邮件旁编辑回复；发送前确认收件人、抄送、主题、正文和附件；调用 Mailpit/SMTP Provider。
  - 验收：模型没有直接发送权限；只有用户点击“审核并发送”才能调用发送 API；失败可重试且不会重复发送。
  - 测试：幂等键、审计记录、发送失败、危险收件人变化和附件确认。
  - 依赖：`MAIL-01`、`MAIL-02`。

- [ ] `MAIL-05` 单一真实邮箱适配器（比赛加分项）
  - 交付：根据可用账号在 Microsoft Graph OAuth 或通用 IMAP/SMTP 中选择一种实现。
  - 验收：令牌或应用密码加密保存，可断开并删除；演示失败时可切换 Mailpit。
  - 依赖：`MAIL-04`。

### 阶段 C：可信文档与 Agent 体验

- [ ] `TRUST-01` 合同版本与变更影响
  - 交付：建立文档族、版本、生效状态和替代关系；比较付款、验收、开票及范围条款变化。
  - 验收：新版本在人工发布前不覆盖现有台账；发布时列出受影响节点、风险和草稿。
  - 依赖：`CORE-01`、`CORE-02`。

- [ ] `TRUST-02` 端到端证据链
  - 交付：展示“文档/邮件 → 事实 → 付款节点 → 流水 → 风险 → 回复”的可点击链路。
  - 验收：每个风险和草稿都能回到具体版本、页码或邮件原文；旧版本证据有明确标识。
  - 依赖：`MAIL-03`、`TRUST-01`。

- [ ] `AGENT-01` 今日行动中心
  - 交付：首页按影响金额、紧急程度和阻塞关系展示最多五项行动。
  - 验收：每项说明“为什么现在处理”和建议动作，可直接跳到对应合同、邮件或核销任务。
  - 依赖：`CORE-03`、`CORE-05`、`MAIL-02`。

- [ ] `AGENT-02` 可审计执行轨迹
  - 交付：记录解析、校验、查找证据、规则计算、草稿生成和人工确认等高层步骤。
  - 验收：可以回放输入、工具结果和最终业务状态，但不展示或保存模型隐藏推理过程。
  - 依赖：`MAIL-03`、`TRUST-02`。

### 阶段 D：DeepSeek Harness 对比实验（后端完成后）

本阶段不进入默认部署，也不阻塞比赛核心功能。只有 `CORE-01` 至 `CORE-05`、`MAIL-01` 至 `MAIL-04` 的后端 API 和自动化测试完成，且评测数据集已经冻结后才能开始。实验期间现有直接模型调用始终是默认路径和故障降级路径。

- [ ] `DSH-01` 冻结直接后端基线
  - 交付：抽象 `AgentRuntime` 接口，将当前模型调用命名为 `DirectRuntime`；冻结模型版本、温度、提示词、工具协议和 Pydantic 输出结构。
  - 验收：不安装 DSH 时所有现有功能和测试保持通过；每次运行记录任务、耗时、Token、重试、结构校验和业务结果。
  - 依赖：`CORE-05`、`MAIL-04`、`QA-01` 至 `QA-05`。

- [ ] `DSH-02` 隔离式 SDK 探针
  - 交付：使用固定版本的 `deepseek-harness-sdk` 建立独立容器、独立 workspace、独立 `DSH_HOME` 和一次性测试会话。
  - 安全：关闭 `session-log-deepseek`，不启用 shell、文件编辑、任意网络访问、子代理或第三方插件；不得读取 `.env`、数据库文件、合同原件或邮箱令牌。
  - 验收：完成一次无业务写入的健康检查，超时或启动失败时自动回退 `DirectRuntime`；DSH 依赖只存在于可选 requirements/Compose profile 中。
  - 依赖：`DSH-01`。

- [ ] `DSH-03` SoloPact 受控工具适配
  - 交付：只向 DSH 暴露查询合同、查询邮件、搜索证据、提出经营承诺和生成回复草稿等白名单工具。
  - 验收：DSH 只能返回“待确认提案”，不能直接写数据库、发布合同版本、确认核销或发送邮件；所有结果再次通过 Pydantic 和业务规则校验。
  - 测试：越权工具、提示注入、跨租户访问、非法参数、超时和重复调用全部被拒绝并记录。
  - 依赖：`DSH-02`、`TRUST-02`。

- [ ] `DSH-04` 双运行时和同模型控制
  - 交付：通过 `AGENT_RUNTIME=direct|dsh` 切换运行时，并保留按任务灰度选择和自动降级能力。
  - 验收：两条路径使用同一个模型端点、相同提示词、相同工具和相同输入；优先使用同一华为云模型，若其工具调用不兼容，则两组都改用同一个实验模型，禁止把模型差异当成 Harness 效果。
  - 依赖：`DSH-03`。

- [ ] `DSH-05` 360 次 A/B 基准评测
  - 数据：20 封邮件分类、10 条付款承诺、10 个证据回复、10 个多步骤任务和 10 个对抗样本，共 60 个案例。
  - 方法：`DirectRuntime` 与 `DshRuntime` 各运行 3 次，共 `60 × 2 × 3 = 360` 次；保存逐项结果和聚合报告。
  - 指标：结构化输出通过率、邮件分类 Macro-F1、工具选择准确率、证据引用准确率、端到端成功率、中断恢复率、P50/P95 延迟、Token、单次成功成本和安全违规数。
  - 目标线：结构化输出 ≥99%，邮件分类 Macro-F1 ≥0.85，工具选择 ≥95%，证据引用 ≥98%，中断恢复 ≥95%，提示注入越权 0/10，未授权写入和重复发送均为 0。
  - 效率线：DSH 的 P95 延迟不超过基线 1.35 倍，Token 不超过 1.25 倍，单次成功成本不超过 1.20 倍。
  - 说明：以上均为采用门槛，不得在实际完成评测前写成项目成绩。
  - 依赖：`DSH-04`、`QA-01` 至 `QA-06`。

- [ ] `DSH-06` 采用决策与报告
  - 采用条件：安全指标全部通过，且多步骤成功率比基线提高至少 8 个百分点，或中断恢复能力带来可量化收益，同时满足延迟、Token 和成本门槛。
  - 未通过：默认保留 `DirectRuntime`，只借鉴 DSH 的插件、执行轨迹和会话设计；不得为了技术名词强行引入运行依赖。
  - 交付：生成可复现的 CSV/JSON 原始结果、指标图表、失败案例分析和最终技术决策记录。
  - 依赖：`DSH-05`。

## 5. 比赛演示主线

比赛前新增功能必须服务于以下流程：

`收到验收邮件 → Agent 分类并关联合同 → 人工确认验收事实 → 激活付款节点 → 导入流水并识别部分付款 → 发现逾期 → 生成并审核回复 → 发送至演示邮箱 → 从客户回复中提取付款承诺 → 加入今日行动`

三分钟演示只展示其中最稳定、最能体现差异化的步骤；完整流程保留在在线 Demo 中。
